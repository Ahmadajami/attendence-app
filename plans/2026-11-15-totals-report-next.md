# Totals report: sorting, person search, overtime sheet, percent of required hours

**Status:** to do
**Date:** 2026-11-15
**Goal:** the `/reports` page (T1) can be sorted and searched, a click on a person opens a sheet that explains that person's overtime (instead of the attendance page), and a frontend-only input shows each person's hours as a percentage of required hours.

Builds on T1 (`plans/2026-11-13-follow-odoo-configurable.md`). Real data: CLAUDE.md §1; counts and IDs only in notes.

## 1. Decisions (proposed; they become approved when the user answers §4)

| ID | Status | Decision | Why |
|---|---|---|---|
| RP1 | proposed | **Sort any column of the person table, ascending or descending.** Click a header to sort; the default is by name. The sort is kept in the URL (`sort=<column>&dir=asc\|desc`) so reloads and the Excel export match the page. "Date" sorting belongs to the day list inside the person sheet (RP3), since the table has one row per person and no dates | The table has no date column; sorting by the numbers answers "who has the most overtime" |
| RP2 | proposed | **Person search is server-side:** a text box filters rows by name (English or Arabic) or employee number, kept in the URL as `q`. The Excel export uses the same filter | A search that only hides rows on screen would let the export differ from the page |
| RP3 | proposed | **The person sheet replaces the attendance page for overtime.** A click on a name opens a side sheet (`ui/sheet`) with that person's days in the page's date range, one row per day, sorted by date asc or desc. Each row shows the day, shift, required, worked, overtime, paid and unpaid extra, late, shortage, and a plain-language reason for the overtime. The sheet's data is read-only and is opened by a URL parameter (`person=<id>`), so a reload keeps it open | The user needs to see why the overtime is what it is without leaving the report |
| RP4 | proposed | **Percent of required hours is a frontend calculation only.** One percent input (default 100 %) at the top of the page. For each row: target hours = required × input %; the row shows worked hours, the target, the difference, and the worked share of required (worked ÷ required). Nothing is stored and it is not in the Excel export | Asked for as a frontend input; storing a percentage would need a rule decision |
| RP5 | replaced by RP13 | ~~No money in this task.~~ | Superseded when the user confirmed the salary rules (2026-11-15) |
| RP6 | proposed | **The overtime reason is built from ids and rule names** (from `day_result.explanation`, which holds "ids, rule sources and steps only"). Each reason is a message key in `messages/en.json` and `messages/ar.json`. No absence reason or health detail is shown | CLAUDE.md §1 and the day-result rule |
| RP7 | approved (user, 2026-11-15) | **Day rate = monthly salary ÷ 30**, always, whatever the month's length | The user's rule |
| RP8 | approved (user, 2026-11-15) | **Overtime counts only if the employee's assigned pattern has overtime enabled.** If it is off, extra hours are not eligible overtime. The switch exists per pattern (plan §2, "Overtime on / off: built, per pattern") | The user's rule; reuses the existing setting |
| RP9 | approved (user, 2026-11-15) | **Required hours come from the assigned pattern for the selected range**, calculated dynamically (the sum of each day's required minutes) | The user's rule; the cap depends on the range |
| RP10 | approved (user, 2026-11-15) | **Overtime cap = required hours × configured % ÷ 100.** The % is typed by the user each time; no value is hard-coded (no default: Q-RP5) | The user's rule (example: 25 % of the required hours) |
| RP11 | approved (user, 2026-11-15) | **Overtime multipliers come from the pattern's configuration** (the "Overtime rates per pattern" built in the settings table), never 1.25 or 1.5 in code | The user's rule; the rates already exist per pattern |
| RP12 | approved (user, 2026-11-15) | **Shortage is calculated from the pattern's required hours, with no grace** (user: "no grace"). The shift's `graceMinutes` (default 15, `LATE_GRACE_MINUTES` in `src/lib/roster/rules.ts`) stays for the late status only and is not used in shortage | The user's answer; the grace is per shift, not a system setting |
| RP15 | approved (user, 2026-11-15, from the Odoo screenshot) | **Balance = Overtime − Shortage.** The screenshot's figures match: overtime +39:52 − shortage 2:24 = +37:28 | Shown by the user's reference screenshot |
| RP16 | approved (user, 2026-11-15) | **Hour rate = day rate ÷ the shift's required hours, used for both overtime and shortage** (answer "both" to Q-RP4). Example: a 9-hour shift at a 600 monthly salary gives a day rate of 20 and an hour rate of 20 ÷ 9 | The user's answer |
| RP17 | approved (user, 2026-11-15) | **Overtime cap blank = no cap** (Q-RP5). A cap is only applied when a percent is typed | The user's answer |
| RP18 | approved (user, 2026-11-15) | **A switch "Deduct shortage from salary" on the page, default off, frontend only.** When on, the deduction = hour rate × shortage hours (RP16), subtracted from the base pay. When off, shortage is shown in hours only. The switch state is not stored, not in the URL and not in the export | The user's answer to Q-RP7: a switch, default off |
| RP13 | approved (user, 2026-11-15) | **The monthly salary is typed on the page each time it is needed.** It is not saved to the database or persisted by the backend, and it is not in the Excel export. This replaces RP5 | The user's rule |
| RP14 | proposed | **The Odoo attendance summary is the visual reference** for the columns Required, Worked, OT, Shortage and Balance. Balance = overtime − shortage (RP15). No other rule is added | The user's instruction |
| RP19 | approved (user, 2026-11-15) | **Overtime pay uses the pattern's multiplier of each day.** The multiplier is the day's stored `ot_rate` (work day, off day or holiday rate from the pattern) | The user's answer: overtime pay on the pattern's multiplier |
| RP20 | approved (user, 2026-11-15) | **When the cap cuts minutes, the cut is pro-rata over the days.** Each day keeps the same share of its eligible minutes (capped ÷ eligible), so it keeps its own multiplier | The user's answer (recommended): the result does not depend on the order of the days |
| RP21 | approved (user, 2026-11-15) | **Two rosters in one range: each day uses its own shift's required hours.** Hour rate of a day = day rate ÷ that day's required hours; overtime pay and shortage deduction are summed per day | The user's answer (recommended): the total is exact when hours change |
| RP22 | approved (user, 2026-11-15) | **Shortage is shown in hours. The deduction runs only when the page's switch is on** (RP18, default off, not stored). The deduction is the per-day hour rate × that day's shortage hours | The user's answer (recommended) |
| RP23 | approved (user, 2026-11-15) | **A day with no required hours (off day or holiday work) uses the hours of the shift worked that day** (start to end). If the day has no shift, its hour rate is undefined: its overtime and shortage are not paid, and the reason says so | The user's answer (recommended). A rule the plan did not give, so the user decided it |
| RP24 | default (agent, 2026-11-15, not yet confirmed by the user) | **Credit extra pay (the Friday Prayer credit left over after the shortage, `creditExtraMinutes`) is paid at the day's hour rate, with no multiplier and no cap.** Not overtime, so it is not in the eligible or capped minutes | The rule says "paid as extra time, not overtime" (FP1); the rate is the reading of "extra time" the agent chose. The user must confirm |
