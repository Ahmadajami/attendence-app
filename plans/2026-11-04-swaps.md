# Swaps: self swap and employee swap, from request to roster

**Status:** in progress (approved 2026-11-04 with every default kept; Phases 1–4 built, waiting for the user's manual check §6)
**Date:** 2026-11-04
**Goal:** HR records a **self swap** (a person moves their own off day) or an **employee swap**
(A's work day goes to B, with an optional return date) as a **request**; approving it changes
the roster through one-off shifts and recomputes the days; rejecting leaves the roster as it is;
cancelling an approved swap puts the roster back. Every step is audited and shows in the days'
History.

**Replaces** Phase 6 (tasks 6.1, 6.2) of `plans/2026-11-01-pattern-pay-holidays-missions.md`;
the swap decisions there (**PR25–PR29**, approved 2026-11-02) stay in force and are not repeated
here. **Lane:** `app/main`, one commit per phase, plan file included. Resume point = the first
unticked box.

## 0. Starting point (checked 2026-11-04)

Already built (pay plan Phases 1–3):

  reason, state `pending | approved | rejected | cancelled`, requested / decided / cancelled by
  and when, decision note, cancel reason. DB checks: B iff employee swap and B ≠ A; second date
  required for a self swap and ≠ first; reason not blank; decision and cancel fields match the
  state (a cancel needs a reason). **No migration is needed.**
- Table `roster_override` with `swap_group_id`; one active override per person and date (unique
  index). No service writes overrides yet.
- Pure `src/lib/roster/swaps.ts` (10 tests): `sameScope` (Sun–Sat week or calendar month),
  `checkSwap` → 12 issue codes (`same_date`, `scope`, `missing_date`, `a_not_working`,
  `a_not_off`, `b_not_working`, `b_not_off`, `o_not_off`, `absence`, `override`, `holiday`,
  `inactive`), `swapOverrides` → the override rows.
- Roster and pay: `rosterDay` gives `swapGroupId` / `swapRole` (`swap_on`, `swap_off`); the day
  result pays a "pay as overtime" swap day as off-day work; working an own off day without a swap
  sets "Unauthorised swap" (PR28). `listApprovedSwaps` feeds the recompute. Log cause `swap` and
  source `swap` exist.
- The daily table already shows **Swap: works / Swap: off** tags (day-tags plan).
- Permission keys: `attendance.record` (create), `roster.manage` (approve, reject, cancel), PR29.
- Reusable: `findPeople` remote query (PR45), `DayTagPopover`, History sheet with cause links.

| # | Decision | Why |
|---|---|---|
| SW1 | One page **`/changes`**, sidebar **Swaps** (`roster.manage` or `attendance.record` to see it): tabs **Pending**, **Approved**, **Rejected & cancelled**; GET filters month (default this month, by first date) and person (the PR45 combobox, A or B); a **New swap** button | The pay plan named `/changes` (room for other roster changes later); filters as on the daily page |
| SW2 | **New swap sheet:** kind (self / employee), person A (and B), dates (self: work day W and off day O; employee: date D and optional return date D2), scope (week / month), **pay as overtime**, reason (required). While typing, a **live preview** (remote query `previewSwap`) shows each person's planned day on each date and what the swap makes of it (e.g. "A · Tue 05: D shift → off"), and lists the issues in words. **Blocking issues refuse the save** (the same `checkSwap` runs on the server) | Pay plan §5 screen; HR sees the effect before saving; no stale request is stored |
| SW3 | **Save and approve:** a user with `roster.manage` gets a second button that creates the request and approves it in one step (two audit rows: requested, approved). The plain **Save request** leaves it pending | One operator today: saves a click; the request / approval trail stays the same for later (PR25) |
| SW4 | **Approve** re-runs `checkSwap` with `swapId` (PR27), then in **one `batch`**: request → `approved` (decided by / at, optional note), the `swapOverrides` rows (`swap_group_id` = request id, `reason` = the request's reason, created by the approver), `markNeedsRecompute`, audit `swap.approve`; then `recomputeAfter` for both people over the swap's dates, cause `swap` / request id. A clash on the unique override index (saved meanwhile) → "changed meanwhile, reload" | Reuses the override machinery and the edit log (PR22, PR23) |
| SW5 | **Reject** a pending request with a **note (required)**: state `rejected`; the roster does not change. **Cancel**: a pending one is withdrawn (no overrides exist); an approved one cancels **all its overrides together** (`cancelled_at` / `by`) in the same batch and recomputes; a **reason** is required (DB check). Nothing is deleted | PR25, PR27; never hard-delete (template §6) |
| SW6 | **No editing** of a request: withdraw (cancel) and create a new one | Keeps the trail simple; a request is small |
| SW7 | Another **pending** request touching the same person and date is a **warning** at creation (shown, not blocking); the second approval then fails on `override` | Both may be legitimate drafts; only one can apply |
| SW8 | **Audit** `swap.request`, `swap.approve`, `swap.reject`, `swap.cancel` with ids, kind, dates, scope and state only (no reason or note text). The days' **History** lines from a swap link to the request (`/changes?swap=<id>`, which opens its detail sheet) | CLAUDE.md §1; the History cause link was left for this phase |
| SW9 | **Markers and entry points:** roster preview cells of swap days get a ⇄ mark and a title (Swap: works / off); the **Swap** tag popover on the daily page gets "Open the swap"; the employee day panel gets **New swap**, opening `/changes` with A and the date filled | One click from where a swap shows to the swap itself |
| SW10 | **Person picker:** a form-agnostic `PersonPicker` (bindable `value` = staff id, server search via `findPeople`) for A and B; the daily page's `PersonCombobox` keeps its GET-form role | The combobox posts `staff` / `q` hidden inputs; a Superforms field needs a bindable id |
| SW11 | Swaps on **past dates** are allowed (PR11): the days are recomputed and their History shows the swap. **Holidays** stay refused (`checkSwap` `holiday`) | HR records swaps after the fact; a holiday is off for everyone already |

## 2. Rules in pure code (Vitest, no DB)

- `src/lib/roster/swap-moves.ts` (new): `swapMoves(plan, dayOf)` → one line per person and date:
  `{ staffId, date, before: shiftId | null, after: shiftId | null, role: 'swap_on' | 'swap_off' }`,

  employee swap with and without return date, an invalid plan gives no moves.

  reason required). Tests mirror the DB checks.

## 3. Services

- `swaps.crud.ts` (extend): insert request; list requests by state, month and person with A / B
  names and numbers and the requester / decider names; find one; set state (approve, reject,
  cancel) with a `state = <expected>` guard so a double click or a stale tab cannot decide twice;
  insert overrides; cancel overrides by `swap_group_id`; pending requests touching person-dates
  (SW7). Writes return unexecuted queries (template rule).
- `swaps.bl.ts` (new): `previewSwap`, `createSwap` (+ optional approve, SW3), `approveSwap`,
  `rejectSwap`, `cancelSwap`, `listSwaps`, `getSwap`. Each loads the two people's roster days for
  the swap's dates with the existing roster loader, checks permissions (PR29), audits (SW8) and
  recomputes (SW4, SW5).
- `src/lib/remote/swaps.remote.ts`: `previewSwap` query (debounced by the sheet, 300 ms, runed
  `Debounced`), `attendance.record`.

## 6. Manual check (by the user, on `http://127.0.0.1:5174`, `_e2e`)

1. Sidebar **Swaps** opens `/changes` on **Pending**, this month; `/ar/changes` is right to left.
2. **New swap** (page) **→ Self swap**: pick a made-up person, a work day W and an off day O in the same
   week: the preview shows "W: shift → off" and "O: off → shift"; no issues.
3. Move O to the next week with scope **week**: the issue "not in the same week" shows and
   **Save** is refused; switch scope to **month** (same month): accepted.
4. Pick a W that is already off: "not working on that day".
5. Save the request: it is **Pending**; the roster preview and the daily page have **not**
   changed.
6. **Approve**: it moves to **Approved**; on the daily page W shows **Swap: off**, O shows
   **Swap: works** with W's shift; the History of both days shows the swap as the cause.
7. **Employee swap** on D where A works and B is off: approved → A off, B works A's shift.
8. Same with a **return date** D2: on D2 B is off and A works B's shift.
9. B also works on D: "B is not off on that day", save refused.
10. **Reject** a pending one without a note: refused; with a note: **Rejected**, roster unchanged.
11. **Cancel** an approved swap with a reason: **Cancelled**; the roster and the daily page are
    back as before; History shows the change back.
12. **Save and approve** creates it directly as Approved.
13. Roster preview (pattern or team page): swap days show ⇄ with the title Swap: works / off.
14. Daily page: the **Swap** tag's popover has **Open the swap**, which opens its detail.
15. History of a swap day: **Open the cause** opens the swap's detail on `/changes`.
16. Employee page → Schedule → a day → **New swap**: the New swap page opens with the person and
    date.
17. New swap page, **Employee swap**: pick A, then B on the first click; the grid shows A's and
    B's month (codes = work, O = off). Tap a day: it fills the swap date and rings it; tap
    another: it fills the return date. The arrows change the month.
18. Typing the reason does not reload the preview or the grid (no spinner while typing).
19. Save and approve: the page opens `/changes` on that swap's detail, under **Approved**.

## 7. Not in this plan

- Other one-off roster changes (a single extra shift, a moved shift) on `/changes`: later.
- Requests by employees or supervisors themselves, notifications and emails (after login, S8).
- Approver chain enforcement and "nobody approves their own request" (PR29, after login).
- Closed or locked periods (when periods exist).
- Swaps of part of a shift or between different shifts on the same day.
